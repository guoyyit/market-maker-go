# 崩溃恢复

## 持久化内容

存储目录（引擎 `StoreDir`）下有两个文件：

- `state.json`：完整状态快照；
- `risk.log`：保护状态进入/退出的追加式 JSONL 审计日志。

`state.json` 包含：

| 字段 | 用途 |
| --- | --- |
| `trades` | 已生效成交回报**全集**，是持仓的唯一事实来源 |
| `position` | 冗余持仓，仅用于一致性校验 |
| `last_intent` | 最近一次提交成功的报价意图 |
| `last_tick` | 最近一帧有效行情（跳变/心跳基准） |
| `risk` | 风控状态、最后有效序号/中间价/时间 |
| `pricer` | 各侧各档代号、已提交代号/价格指纹、RNG 抽取计数与缓存抖动 |
| `config` | 最近一次生效配置（含热更新结果） |
| `last_tick_seq` / `last_trade_seq` | 已处理输入的序号水位 |

快照采用「写临时文件 → fsync → 原子 rename」。崩溃后只会读到完整的
上一版或当前版，不会读到半写文件。每个状态提交点（行情、成交、配置、
保护流转处理完成后）同步落盘。

## 启动恢复流程（`Engine.Recover`）

1. 读取快照；无快照视为首次启动，正常空状态开始。
2. **按成交集合重算持仓**：清空账本后依次 `Rebuild(trades)`，
   集合内重复 ID 只生效一次。若冗余 `position` 与重算结果不一致，
   以重算结果为准（打印告警），避免脏持仓驱动报价。
3. 恢复行情/成交序号水位与最后有效行情。
4. 恢复最近一次生效配置，并同步给报价生成器与风控监视器。
5. 恢复风控状态，并从 `risk.log` 加载全量审计历史。
6. 恢复报价生成器代号表、已提交指纹与 RNG 位置（空转对齐抖动序列）。
7. 重建挂单：
   - 若处于 `PROTECTED`：**先全量撤单，不重建任何报价**，清空意图；
   - 若处于 `NORMAL` 且有有效行情：用「最后有效行情 + 重算持仓」重新生成
     意图，与网关现状对账后提交，并固化代号/指纹与最近意图。
8. 以重算后的真实状态再落一次盘，收敛任何历史不一致。

## 不重复挂单 / 不丢失意图

- 网关以 `ClientOrderID` **幂等**受理：同一在挂单重复 `Submit` 返回同一
  受理记录、不产生第二条挂单，因此恢复时重复提交在挂 ID 是安全的。
- 已成交/已撤销 ID 为终态，禁止复用；报价生成器的代号与"已提交代号/指纹"
  一并持久化，恢复后能正确判断哪些档位需要用**新代号**补挂，
  既不会复活已成交旧单，也不会丢失该档位的报价意图。
- 即使代号表缺失（向前兼容），意图价格仍由最后行情与持仓确定性重放得到。

## 与成交回报的一致性

恢复后的持仓恒等于「对持久化成交集合按规则重算」的结果：
买入 `+Qty`、卖出 `-Qty`、相同 `Trade.ID` 只计一次。
在线处理与重启重算共用同一套去重/累加规则，结果与到达顺序无关。

## 乱序/重复输入在恢复后仍然成立

序号水位（`last_tick_seq`、`last_trade_seq`）与成交 ID 集合都从快照恢复：
崩溃前后注入的旧行情、重复或迟到成交回报依旧被忽略，处理结果确定。
