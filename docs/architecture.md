# 架构与数据流

## 总览

```
            Tick / Trade / Config / Timer
                        │  (in-process channel)
                        ▼
                 ┌─────────────┐
                 │   Engine    │ 单 goroutine 状态机
                 └─────────────┘
        ┌───────────┬─────────┴───────────┬──────────────┐
        ▼           ▼                     ▼              ▼
   risk.Monitor pricing.Generator     ledger.Ledger   config.Manager
        │           │                     │
        │           ▼                     │
        │      book.Reconciler ──► gateway.InMemory ──► Fills chan
        ▼                                │
   risk.log (JSONL)                      ▼
                              store (state.json 原子快照)
```

全部组件都在同一进程内，网关为内存实现，不依赖任何外部服务。

## 单循环事件处理

引擎只有一个处理 goroutine：

1. 从输入通道取一条事件；
2. 分发到对应处理器，串行更新全部状态；
3. 需要时调整网关挂单并落盘；
4. 产出一条 `Observation`（持仓、风控状态、在挂报价、忽略/拒绝标记、
   本事件的保护流转）。

串行处理使"结果仅由输入序列决定"，无需在领域状态上加锁；
网关、账本、风控内部的锁仅用于构造/恢复阶段与外部只读查询。

## 各事件处理要点

### 行情 `TickEvent`

1. `Seq <= lastTickSeq` → 判定为重复或迟到旧帧，**忽略**（不覆盖任何状态）。
2. 交风控监视器判定：异常 → 记录流转、全量撤单、清空意图、持久化；
   正常（含从保护恢复）→ 更新最后有效行情。
3. `NORMAL` 下以最新行情与持仓生成意图，代号轮换后增量对账，成功则固化
   意图/代号/指纹并持久化。

### 成交 `TradeEvent`

1. 成交 `ID` 已在账本 → 重复回报，忽略。
2. 成交 `ID` 为新值 → **无论序号新旧都生效一次**：乱序（迟到的旧序号）
   回报同样入账。只有完全相同的重复成交回报（同 `Trade.ID`）才被忽略，
   同一笔成交不会重复影响持仓。
3. 账本入账更新持仓；`lastTradeSeq` 仅推进为已见最大序号
   （供崩溃恢复后播种网关成交序号），不再用于丢弃回报；被成交档位代号加 1。
4. `NORMAL` 且有行情时立即重新对账（用新代号补挂、套用价格/数量倾斜与
   上限裁剪），
   再持久化。

由于持仓是已接受成交集合的累加、报价由"最终持仓 + 最后行情"确定性重放，
同一组成交回报以任意顺序注入，最终持仓与在挂报价集合完全一致。

### 配置 `ConfigEvent`

校验 → 原子替换三处参数 → 立即对账 → 持久化；非法配置返回拒绝标记，
不影响在挂报价。

### 定时器 `TimerEvent`

只做心跳检查；超时则记录流转、全量撤单、清空意图、持久化。

## 容错与一致性保证汇总

- 旧行情不覆盖新状态（序号水位）。
- 成交以 `Trade.ID` 幂等去重：只有完全相同的重复回报被忽略；新 ID 的乱序
  （迟到旧序号）回报仍生效一次，结果与到达顺序无关、只由成交集合决定。
- 行情仍以序号水位过滤：迟到的旧行情不覆盖新状态（行情与成交语义不同）。
- 任何时刻对账完成后，网关在挂集合等于最近意图。
- 异常行情先全撤、再进入保护，恢复前不挂新单；流转全程审计。
- 持仓、意图、风控、代号/随机流、配置均持久化，重启不重复挂单、不丢意图，
  持仓恒等于成交重算结果。
- 固定种子与相同输入下输出逐条一致。
